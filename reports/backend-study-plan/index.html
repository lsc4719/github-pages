01. 기초는 쌓였고, 연결할 차례입니다

진도 판단은 학습 이슈의 체크 상태를 기준으로 했습니다. 읽었다는 기록은 확인할 수 있지만, 구현 숙련도나 실제 공부 가능 시간은 아직 알 수 없습니다.

확인된 학습
Kurose & Ross 1~2장, JVMS 2장, dev.java Annotations, Reactor Core Features, Spring Start Here 1~6장.
바로 이어갈 곳
Spring Start Here 7장. 공개 요약이 있어도 이슈에는 미완료이므로, 짧은 설명·실행 확인 후 넘어갑니다.
열려 있는 갈래
WebFlux에서 Netty·Gateway로 내려가는 흐름, SQL에서 JPA·Spring Transaction으로 올라오는 흐름, Docker 기반 지식, AWS SAA·Kubernetes.

계획상 판단: 진도가 느린 이유를 의지 문제로 단정할 수는 없습니다. 다만 자료가 책·명세·공식 문서·자격증 강의로 넓게 펼쳐져 있고, “이번 주에 어디서 멈출지”는 덜 분명합니다. 우선 선택할 갈래와 완료 단위를 줄여보는 것이 좋겠습니다.

Knowledge map은 장기 참고 지도입니다.

모든 자료를 순서대로 완독할 필요는 없습니다. 당분간 본교재는 Spring Start Here 하나, 보조 자료는 그 주의 질문을 해결할 공식 문서 한 절로 제한합니다. 1~6장은 막힌 개념만 다시 보세요.

02. 주 3시간, 세 번만 약속합니다

기본 예시는 화요일 45분·목요일 45분·주말 90분입니다. 요일과 시각은 생활에 맞춰 옮기되, 첫 2주는 시간을 늘리지 마세요. 별도의 알림이나 일정은 등록하지 않았습니다.

A · 읽기 45분

지난 내용 떠올리기 5분 → 해당 절 읽기 30분 → 오늘의 질문·다음 행동 기록 10분.

B · 실행 45분

예제 실행·변형 35분 → 요청 결과나 SQL 로그 하나 저장 10분.

C · 연결 90분

기억으로 설명 10분 → 내 API에 적용 60분 → 확인·이슈 기록 20분.

주간 성공 기준: 실행하거나 재현한 결과 하나와, 자료를 닫고 쓴 설명 3문장. 정리 글을 예쁘게 만들거나 자료를 추가 수집하는 일은 완료 조건에 넣지 않습니다.

각 주의 “완료”는 읽기·실습의 통과 기준이며 정해진 시간 안의 성취를 보장하지 않습니다. 첫 2주 결과로 분량을 조정합니다.

03. 같은 API를 8주 동안 키웁니다

실습 주제: 학습 기록 API. 항목 생성·단건 조회·완료 처리 세 기능만 만듭니다. 처음에는 메모리에 저장하고, 3주차부터 PostgreSQL을 연결합니다. 로그인·프런트엔드·배포·검색·메시징은 이번 범위에서 제외합니다.

저장은 study_item(id, title, completed, created_at), 변경 기록은 study_event(id, item_id, action) 정도면 충분합니다. 기존 실습 프로젝트가 있으면 그것을 재사용해도 됩니다.

WEEK 02 · HTTP와 API

생성·조회·완료 처리 연결하기

A · 읽기
Spring Start Here의 REST 서비스 부분과 Spring MVC의 Annotated Controllers 중 요청 매핑·응답 처리. 네트워크 2장에서 본 HTTP 개념을 여기서 회상합니다.
B · 실행

WEEK 03 · 저장의 기초

SQL과 JDBC로 PostgreSQL 연결하기

A · 읽기
Spring Start Here의 데이터 소스·JDBC 부분. SQL이 낯설면 INSERT·SELECT·UPDATE와 기본 키부터 봅니다.
B · 실행
학습용 로컬 DB 하나를 준비합니다. 테이블을 만들고 SQL 세 종류를 직접 실행한 뒤, JdbcTemplate으로 조회 하나를 연결합니다.
C · 연결
메모리 저장을 JDBC로 바꿉니다. 앱을 재시작한 후에도 생성 항목이 남는지 확인합니다.

완료: 재시작 후 조회 결과 하나. “Controller → Service → JDBC → DB”의 역할을 설명합니다. 설치가 막히면 환경 준비와 조회 하나까지만 하고 한 주 연장합니다.

WEEK 04 · 실패와 일관성

두 번의 쓰기를 함께 되돌리기

A · 읽기
Spring Start Here의 트랜잭션 부분과 공식 문서의 @Transactional 기본 프록시 모드·롤백 규칙.
B · 실행
완료 처리 시 항목 UPDATE와 변경 기록 INSERT를 함께 실행합니다. 두 쓰기 사이에 의도적으로 RuntimeException을 던집니다.
C · 연결
Controller에서 별도 Service 빈의 public 트랜잭션 메서드를 호출하고, 실패 뒤 두 테이블을 직접 조회합니다. 전후 결과를 비교합니다.

완료: 실패 후 두 변경이 함께 롤백된 증거. 기본 프록시 모드에서 같은 객체 내부 호출이 왜 주의점인지 설명합니다.

WEEK 05 · 동시 접근

격리 수준과 잠금 한 장면 재현하기

A · 읽기
PostgreSQL Transaction Isolation의 Read Committed·Repeatable Read, Explicit Locking의 행 잠금 부분만 읽습니다.
B · 실행
DB 세션 두 개를 열어, 한 트랜잭션 안에서 같은 SELECT를 반복하고 다른 세션의 커밋 전후를 관찰합니다. 격리 수준을 바꾸어 비교합니다.
C · 연결
두 세션에서 같은 행을 UPDATE해 대기를 관찰하고 COMMIT/ROLLBACK으로 해제합니다. 실행 순서·관찰 결과를 짧게 남깁니다.

완료: 세션 A/B의 실행 순서와 결과 한 장. “트랜잭션이 있다고 모든 동시성 문제가 해결되는가?”에 답합니다. MVCC 구현 전체는 다음으로 남깁니다.

WEEK 06 · 조회 비용

인덱스 전후 실행 계획 비교하기

A · 읽기
PostgreSQL Using EXPLAIN의 기초와 EXPLAIN ANALYZE. 비용 추정·실제 행 수·실행 시간을 구분합니다.
B · 실행
학습 데이터 수만 건을 만들고, 완료 여부·생성 시각으로 필터링하는 SELECT를 정합니다. ANALYZE 후 실행 계획을 저장합니다.
C · 연결
조회에 맞는 인덱스 하나를 추가해 같은 쿼리의 계획을 비교합니다. 인덱스 사용 여부와 데이터 선택도를 설명합니다.

완료: 전후 계획 2개와 설명 3문장. 인덱스를 사용하지 않거나 빨라지지 않아도 원인을 설명하면 통과입니다. 시간 수치 하나로 성능을 일반화하지 않습니다.

WEEK 07 · 추상화 연결

JDBC에서 JPA로 조회 하나만 바꾸기

A · 읽기
Hibernate ORM User Guide에서 단일 엔티티 매핑·영속성 컨텍스트·flush 개념만 찾습니다. 보유한 Spring Data JPA 문서는 저장소 조회 한 가지에 한정합니다.
B · 실행
학습 항목 엔티티 하나와 단건 조회 하나만 JPA로 구현합니다. 연관관계·캐시·N+1은 아직 펼치지 않습니다.
C · 연결
실제 SQL 로그를 보고 JDBC 조회와 비교합니다. 가능하면 같은 트랜잭션 안의 변경 감지도 확인합니다.

완료: 같은 조회의 Java 코드·실행 SQL 비교. JPA가 SQL·트랜잭션 이해를 어디까지 대신해 주는지 설명합니다. 변경 감지는 시간이 남을 때 합니다.

WEEK 08 · 정착

실패를 검증하고 처음부터 재실행하기

A · 읽기
Spring Start Here의 테스트 부분에서 필요한 단위·통합 테스트 예제만 봅니다. 지금 프로젝트의 테스트 도구 버전에 맞춥니다.
B · 실행
빈 제목 거절, 정상 생성·조회, 두 쓰기의 롤백을 확인하는 테스트를 정리합니다. DB 테스트는 PostgreSQL로 하고, Testcontainers는 이미 준비된 경우에만 사용합니다.
C · 연결
앱·DB 시작 명령, 예제 요청, 테스트 실행법을 README에 적고 그대로 재실행합니다. 1주차 질문에 다시 답합니다.

완료: 실행 가능한 API 하나, 핵심 테스트 결과, “요청이 저장되고 실패하면 어떻게 되는가”를 설명하는 1쪽 기록. 테스트 메서드 자체의 자동 롤백만 보고 서비스 롤백이 검증됐다고 판단하지 않습니다.

8주 목표는 완독이 아니라 한 흐름의 이해입니다.

책의 MVC 화면·스코프·외부 서비스 호출 부분은 이번 API에서 필요한 만큼만 봅니다. JPA는 이 책 밖의 보충 주제입니다. 따라서 이 계획을 마쳐도 Spring Start Here 전체 완독으로 표시하지 않습니다.

04. 밀려도 다시 시작할 수 있게

  • 바쁜 주: 20분씩 두 번만 합니다. 질문 하나를 읽고, 예제나 SQL 한 번을 실행합니다. 진도가 제자리에 있어도 학습 리듬은 성공으로 기록합니다.
  • 한 번 빠졌을 때: 보충 공부를 예약하지 말고 다음 세션에서 같은 작업을 이어갑니다. 뒤 주차의 새 주제를 겹쳐 시작하지 않습니다.
  • 완료 기준이 남았을 때: 같은 주차를 한 주 연장합니다. 주 1시간 30분 정도라면 각 주차를 2주로 나누어 총 16주로 진행합니다.
  • 30분 이상 막혔을 때: 기대 결과·실제 결과·가장 작은 코드/SQL을 기록합니다. 다음 공부는 이 문제부터 시작하고, 관련 없는 문서 탐색은 멈춥니다.
  • 2주 연속 부담스러울 때: 읽는 범위를 절반으로 줄입니다. 반복해서 시간을 못 낸다면 주 3시간 가정을 수정합니다.

첫 2주 뒤에 볼 것은 세 가지입니다

예정 6회 중 몇 번 시작했는지, 결과를 하나라도 남겼는지, 다음에 무엇을 할지 분명한지 확인합니다. 4회 이상 시작했다면 분량 유지, 3회 이하라면 다음 주 목표를 절반으로 줄입니다. 이는 이 계획의 조정 기준이며 능력 평가가 아닙니다.

05. 다른 주제는 언제 돌아올까요?

업무에서 급하게 필요한 주제가 없다면 8주 동안은 아래 자료를 대기시킵니다. 공부를 포기하는 것이 아니라, 다시 시작할 조건을 정하는 것입니다.

WebFlux → Reactor Netty → Netty → Gateway

현재 MVC·저장 흐름을 설명한 뒤 다음 4주 후보로 둡니다. Reactor Core Features는 이미 읽었으므로 처음부터 재독하지 말고 scheduler·오류·backpressure를 작은 코드로 확인하며 WebFlux로 연결하세요. 실제 업무가 Gateway/WebFlux 중심이라면 이 경로를 먼저 택하고 DB 심화 주차를 뒤로 미룹니다. 두 경로를 동시에 진행하지 않습니다.

AWS SAA → Docker → Kubernetes

자격증 마감이 있다면 SAA를 본학습으로 교체합니다. 마감이 없다면 API를 로컬에서 재현한 후 Docker로 실행 환경을 고정하고, 필요한 AWS 배포 경로 하나를 배운 다음 Kubernetes로 넓힙니다. cgroup·namespace는 컨테이너 자원 제한·격리가 궁금해질 때 찾아봅니다.

CSAPP·JVMS·DDIA·네트워크 후속 장

대형 교재와 명세를 동시에 완독 목록에 넣지 않습니다. 쿼리·트랜잭션을 실습한 뒤 DDIA의 관련 주제를 읽고, 스레드·메모리·통신 문제를 만날 때 CSAPP·JVMS·네트워크 후속 장을 연결합니다. 기초 읽기는 한 번에 한 권만 선택합니다.

Kafka·Redis·검색·마이크로서비스·운영
