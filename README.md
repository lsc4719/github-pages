# Reports on GitHub Pages

이 저장소는 공개 HTML 보고서를 GitHub Pages로 제공합니다. 저장소와 게시된 파일은 누구나 볼 수 있으므로 비공개 정보는 넣지 않습니다.

- 보고서 목록: https://lsc4719.github.io/github-pages/

## 구조

```text
index.html                         # 사이트 홈: 보고서 카드와 링크
reports.json                       # 보고서 메타데이터 목록
reports/
  spring-start-here-chapter-7/
    index.html                     # 개별 보고서
.github/workflows/pages.yml        # GitHub Pages 배포 워크플로
.nojekyll                          # 정적 파일을 그대로 제공
```

각 보고서는 `reports/<slug>/index.html`에 놓습니다. 예를 들어 `reports/my-report/index.html`은 `https://lsc4719.github.io/github-pages/reports/my-report/`에서 열립니다. 이미지나 CSS 등 보고서 전용 파일은 해당 디렉터리에 함께 두고 상대 경로로 연결합니다.

## 편집 원칙: 결론 먼저, 필요한 만큼만

- **핵심 결론 → 실행 순서 → DETAILS → 참고자료** 순서로 씁니다. 제목과 첫 1~3문장에 가장 중요한 판단 하나와 이유·첫 행동을 제시합니다. 결론을 읽은 뒤 바로 무엇을 할지 알 수 있어야 합니다. 실행 방법을 배경 설명 뒤로 미루지 않습니다.
- **문서의 중심 질문은 하나로 잡습니다.** 준비 방법을 묻는 문서라면 준비의 우선순위와 실행 계획이 본문 중심입니다. 시험 제도·자격·지난 일정 같은 배경은 뒤의 DETAILS에 모읍니다. 제도 설명, 공부법, 일정, 조언을 동등한 섹션으로 나열하지 않습니다.
- **DETAILS는 앞의 결론을 뒷받침합니다.** 각 절은 결론의 이유, 구체적인 실행 방법, 예외·조건 중 무엇을 설명하는지 분명해야 합니다. 같은 정보를 요약·카드·차트·본문에서 반복하지 않습니다. DETAILS는 후반의 세부 설명을 뜻하며, 핵심 내용을 접기 UI 안에 숨기라는 뜻이 아닙니다.
- **Practical / effective를 우선합니다.** 계획·추천에는 구체적인 할 일, 범위, 판단 또는 완료 기준을 적습니다. 실행과 이해에 도움이 없는 당위·격려·상투적인 추상론은 덜어냅니다.
- **Occam’s razor를 편집 기준으로 삼습니다.** 같은 의미의 반복, 불필요한 산문·섹션·장식을 삭제합니다. 필요한 전제·근거·예외는 보존합니다.
- **개념을 정확하게 추상화하는 설명은 유지합니다.** 역할·경계·인과·트레이드오프를 짧게 설명하고, 적절한 예시나 다이어그램으로 연결합니다. 간결함을 위해 핵심 개념을 모호하게 만들지 않습니다.
- **UI 자체에 대한 설명은 보고서에서 뺍니다.** 화면 크기에 따른 배치, 박스의 길이, 버튼 조작법, 제작·접근성 검증 결과를 본문이나 캡션에 서술하지 않습니다. UI는 레이블과 상태로 설명하고, 검증 범위는 작업 결과나 커밋에 기록합니다. 데이터 해석에 필요한 단위·조건·출처는 남깁니다.
- 사실·해석·계획·가정을 구분합니다. 사실과 수치는 출처로 뒷받침하고, 확인되지 않은 내용을 단정하지 않습니다.

## 디자인과 시각화

- **연한 베이지·아이보리 배경**, 짙은 갈색·차콜 글자, 절제된 세이지·테라코타 포인트를 기본으로 합니다. 시스템 다크 모드에서도 밝은 스타일과 충분한 대비를 유지합니다.
- **주요 개념과 관계는 가능한 한 다이어그램으로 표현합니다.** 흐름·의존·분기·경계를 짧은 노드와 연결선으로 보여 줍니다. 정의·조건·예외는 짧은 설명으로 보완하고, 도식과 같은 내용을 산문으로 반복하지 않습니다.
- 시간 순서는 타임라인, 정확한 대응·비교는 표, 실제 수치·추세는 차트를 사용합니다. 데이터 없는 점수·달성률·우열 차트는 만들지 않습니다.
- **GitHub의 chip/badge처럼 작은 UI를 활용할 수 있습니다.** 주제·계획·상태·필터를 짧게 표시하되, 의미 없는 배지를 늘리지 않습니다. 선택형 chip은 선택 상태와 키보드 조작을 제공하며, 정적 chip을 버튼처럼 보이게 만들지 않습니다.
- 짧은 내용에는 큰 카드보다 글자 위계·구분선·작은 여백을 사용합니다. 중첩 박스, 과한 패딩·그림자·표지, 반복 장식을 피합니다.
- 다이어그램에는 제목과 명확한 방향·분기 조건을 제공합니다. 캡션은 개념·가정·데이터 해석에 필요할 때만 사용합니다. 읽는 방향이나 모바일 재배치를 산문으로 설명하지 않습니다.
- **JavaScript를 자유롭게 활용합니다.** 다이어그램 탐색, 필터, 주차 선택, 비교, 상태 전환 등 이해와 실행을 돕는 인터랙션에 사용합니다. 프레임워크·외부 라이브러리도 필요에 따라 선택하되 불필요한 의존·로딩·복잡성은 줄입니다. 모바일에서 컨트롤과 결과를 함께 확인할 수 있는지 먼저 검증하고, 키보드 조작·선택 상태·성능을 확인합니다. 인쇄/PDF에도 핵심 내용과 참고자료가 남도록 처리합니다.

## 모바일 설계의 참조 가이드

기본 참조는 **GOV.UK Design System의 콘텐츠 중심 설계**와 **WCAG 2.2의 접근성 기준**입니다. 아래 원칙을 적용하되 베이지 색상과 한국어 본문에 맞게 조정합니다.

| 공식 가이드 | 적용 기준 |
| --- | --- |
| [GOV.UK · Layout](https://design-system.service.gov.uk/styles/layout/) | 작은 화면의 단일 열에서 먼저 설계합니다. 데스크톱에서도 본문 폭을 제한합니다. |
| [GOV.UK · Tabs](https://design-system.service.gov.uk/components/tabs/) | 순서대로 읽거나 비교할 핵심 내용은 탭·chip 필터 뒤에 숨기지 않습니다. 제목·목차·문서 내 이동을 우선합니다. |
| [GOV.UK · Details](https://design-system.service.gov.uk/components/details/) | 일부 독자만 필요한 보충 내용에만 펼치기를 사용합니다. 주요 결론과 실행 지침은 노출합니다. |
| [WCAG · Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) | 320 CSS px에서 정보·기능 손실이나 페이지 전체의 양방향 스크롤 없이 읽힐 수 있게 합니다. |
| [WCAG · Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) | 200% 확대에서 글자·내용·기능을 유지합니다. |
| [WCAG · Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | 최소 24×24 CSS px 또는 규정된 예외·간격 조건을 참고합니다. 이 저장소의 독립 조작 요소는 편의를 위해 44px 이상을 목표로 합니다. |

### 작성은 처음부터 Mobile first

- **320~430px 한 열의 읽기 순서를 먼저 설계합니다.** 결론·첫 행동·예시·DETAILS가 작은 화면에서 자연스럽게 이어지는 HTML과 기본 CSS를 먼저 작성합니다. 데스크톱 레이아웃을 만든 뒤 축소하거나 모바일 예외 규칙을 덧붙이는 방식을 기본으로 삼지 않습니다.
- **기본 CSS가 모바일 완성본이어야 합니다.** 본문 폭·글자·여백·다이어그램·비교 목록은 기본값만으로 읽혀야 합니다. 넓은 화면의 보완이 필요한 경우에만 `min-width` 미디어 쿼리로 확장합니다.
- **버튼을 눌러 떨어진 카드의 하이라이트만 바꾸는 UI를 만들지 않습니다.** 질문·설명·관련 예시는 같은 위치에 함께 표시합니다. 위의 조작부와 아래 결과를 번갈아 확인하거나 선택 상태를 기억해야 하는 읽기 흐름을 피합니다.
- **인터랙션은 실제 조작이 필요한 내용에만 추가합니다.** 단순 설명을 읽기 위해 버튼·탭·필터를 누르게 하지 않습니다. 대국의 판 전환처럼 조작 자체가 이해에 도움이 될 때는 컨트롤과 결과를 가까이 두고, 작은 화면에서 변화가 보이는지 확인합니다.
- **홈의 카드형 보고서 목록은 유지할 수 있습니다.** 모바일에서도 배경·테두리로 보고서를 구분하되 고정 높이와 큰 빈 여백은 피합니다.

### 이 저장소의 구현 기본값

- **첫 화면에서 결론과 첫 행동까지 도달하게 합니다.** 반복 소개·장식 배지·큰 표지·여러 줄 메뉴를 줄이고, 본문보다 탐색 UI가 먼저 길어지지 않게 합니다.
- 모바일 본문은 기본 `1.125rem`, 줄 높이 약 `1.65~1.75`, 좌우 여백은 `1rem`을 출발점으로 삼습니다. 짧은 레이블은 `1rem` 이상으로 두고, 제목은 본문을 밀어내지 않게 제한합니다. 이 수치는 저장소의 기본값이며 WCAG의 의무 수치가 아닙니다.
- **목차·주차 이동에 드롭다운(select)을 사용하지 않습니다.** 모바일에서도 보이는 텍스트 앵커 링크로 바로 이동하게 합니다. 결론·첫 행동 뒤에 주요 구간 3개 안팎만 연결하고, 나머지는 명확한 제목과 필요한 위치의 링크로 찾게 합니다. 긴 버튼·chip 메뉴, 고정 목차, 목차만을 위한 접기 UI도 피합니다.
- **핵심 내용은 기본 노출합니다.** 결론과 실행 순서는 위에서 아래로 바로 읽혀야 합니다. 주차별 계획도 기본 노출하고 짧은 제목·번호로 구분합니다. 핵심 내용을 보기 위해 필터·탭·선택 메뉴를 조작하게 하지 않습니다.
- 터치 요소의 실제 영역은 확보하되 그림자·큰 테두리·과한 패딩은 늘리지 않습니다. 정적 주제 표식은 조작 버튼과 구별합니다.
- 다이어그램은 한 열에서 노드·분기·설명의 폭이 자연스럽게 잡히게 합니다. 좁은 화면에서 고정된 다중 열이나 데스크톱 그림 축소를 사용하지 않습니다.
- **가로 넘침이 없다는 것만으로 모바일 검증을 끝내지 않습니다.** 결론에서 첫 행동까지의 스크롤, 메뉴 줄 수, 반복 정보, 한국어 줄바꿈, 주차 간 이동, 뒤로 가기·확대·키보드 조작을 함께 확인합니다. 실제 확인한 너비와 검증 한계는 작업 결과에 기록합니다.

## 참고자료와 본문 링크 표기

- 참고자료·출처는 **문서 하단에 모아** 자료명·기관명 등 의미 있는 이름에 링크를 연결합니다. 숫자만 나열한 참고자료 목록보다 어떤 자료인지 바로 알 수 있는 이름을 우선합니다.
- 본문에는 **대괄호 숫자 형태의 인용 표식을 노출하지 않습니다.** 출처 연결이 필요한 문장에서는 관련 용어·자료명·설명 문구 자체에 하단 참고자료 또는 원문으로 가는 링크를 겁니다. 클릭되지 않는 숫자 표식은 사용하지 않습니다.
- 본문을 읽는 흐름을 끊는 URL 나열을 피하고, 자세한 출처 정보·확인일·보충 설명은 하단에 둡니다. 연결한 자료는 해당 주장이나 수치를 실제로 뒷받침해야 합니다.
- 인쇄/PDF에서도 하단 참고자료의 이름과 출처 정보를 읽을 수 있게 유지합니다.

## 새 보고서 추가하기

1. `reports/` 아래에 영문 소문자와 하이픈으로 된 고유한 디렉터리를 만들고 그 안에 `index.html`을 작성합니다.
2. 루트 `index.html`의 `<section class="grid">` 안에 기존 `article.report-card`를 참고해 날짜, 제목, 요약과 `./reports/<slug>/` 링크를 추가합니다. 제목과 Open report 링크를 모두 새 경로로 바꿉니다.
3. `reports.json`의 `reports` 배열에도 `slug`, `title`, `summary`, `date` (`YYYY-MM-DD`), `path` (`./reports/<slug>/`)를 추가합니다. JSON 문법과 쉼표를 확인합니다.
4. 로컬에서 저장소 루트를 기준으로 `python3 -m http.server 8000`을 실행하고 `http://localhost:8000/`에서 목록과 보고서 링크, 이미지 및 스타일을 확인합니다. 종료하려면 `Ctrl+C`를 누릅니다.
5. 변경 파일을 커밋하고 `main` 브랜치에 푸시합니다. GitHub Actions의 **Deploy GitHub Pages** 워크플로가 자동 배포합니다. Actions 탭에서 성공을 확인한 후 공개 목록과 보고서 URL을 열어 확인합니다. 필요하면 Actions에서 워크플로를 수동 실행할 수도 있습니다.

`reports.json`은 메타데이터 파일이며 현재 홈 페이지가 이를 자동으로 읽지는 않습니다. 따라서 목록에 표시하려면 `index.html` 카드도 직접 추가해야 합니다. GitHub Pages는 저장소 이름이 포함된 `/github-pages/` 아래에서 제공되므로 사이트 루트(`/reports/...`) 대신 상대 경로를 사용합니다.

## 모바일에서 읽기 쉬운 보고서 작성 기준

새 보고서를 만들거나 기존 보고서를 수정할 때는 모바일 가독성을 필수로 확인합니다. 특히 저시력 사용자가 글자를 키워 읽어도 내용을 따라갈 수 있어야 합니다.

- **모바일에서는 내용의 밀도와 스크롤 부담을 확인합니다.** 큰 빈 박스·중첩 카드·과한 내부 패딩·고정 높이·화면을 채우는 표지를 피하고, 짧은 내용에는 박스보다 타이포그래피·구분선·작은 여백을 우선합니다. 터치 영역을 확보하되 박스 전체를 불필요하게 키우지 않습니다.
- **다이어그램은 모바일에 맞춰 다시 배치합니다.** 가로 흐름은 세로로, 분기는 읽는 순서가 분명한 구조로 전환합니다. 노드·연결 관계·조건·캡션은 유지하고 글자를 축소하거나 그림 전체를 작게 줄여 끼워 넣지 않습니다. SVG를 쓰는 경우에도 작은 글자와 화면 잘림을 점검합니다.
- 모바일에서는 본문을 한 열로 배치합니다. 화면 너비에 맞추려고 글자 크기를 줄이지 않습니다. 본문은 최소 `1rem` 이상으로 쓰고, 상대 단위와 충분한 줄 간격을 사용합니다.
- 설명이 긴 비교표는 좁은 화면에서 **제품별 카드 또는 항목별 목록**으로 전환합니다. 각 카드에 제품명, 가격, 장점, 주의점 같은 항목 이름을 함께 표시하고, 데스크톱 표와 같은 내용을 유지합니다.
- 여러 열을 화면 안에 억지로 압축하지 않습니다. 한글이 한두 글자씩 끊겨 세로로 길어지는 표는 사용하지 않습니다. 일반 본문에 `word-break: break-all`을 적용하지 않습니다. 긴 URL 등 필요한 부분에만 별도의 줄바꿈 처리를 합니다.
- 숫자 중심의 짧은 표처럼 표 형식이 꼭 필요한 경우에만 표 영역의 가로 스크롤을 허용합니다. 이 경우 열의 읽기 쉬운 최소 너비를 보장하고, 가로로 넘겨 볼 수 있다는 안내를 제공합니다. 페이지 전체가 좌우로 밀려서는 안 됩니다.
- `<meta name="viewport" content="width=device-width, initial-scale=1">`을 넣고, 확대를 막는 `user-scalable=no`나 `maximum-scale=1`은 사용하지 않습니다.
- 브라우저 글자 확대에도 내용이 잘리거나 겹치지 않도록 고정 높이를 피합니다. 링크와 버튼은 손가락으로 누르기 충분한 크기(권장 최소 44×44 CSS px)로 만듭니다.
- 시스템의 밝은 모드·어두운 모드 모두에서 문서의 밝은 색상 스타일과 충분한 글자 대비를 유지합니다. 색상만으로 추천·주의 등의 의미를 전달하지 않습니다.
- 표를 카드로 바꾸어도 항목 이름과 읽는 순서를 유지합니다. 화면읽기 프로그램이 같은 내용을 두 번 읽지 않도록 하고, 표 머리글을 단순히 숨겨 의미가 사라지지 않게 합니다.

### 게시 전 확인

1. 320px, 360px, 390px, 430px 너비에서 홈과 보고서를 확인합니다. 결론의 핵심과 첫 행동이 바로 보이는지, 설명을 읽느라 실행 순서가 늦어지지 않는지, 목차·주차 이동 드롭다운이 없는지 봅니다.
2. 글자 크기 또는 브라우저 확대를 200%로 높여 잘림, 겹침, 비정상적인 줄바꿈이 없는지 확인합니다.
3. 긴 비교표가 모바일에서 카드나 목록으로 바뀌고, 제품명·가격·추천 이유를 자연스러운 순서로 읽을 수 있는지 확인합니다.
4. 표지·박스·다이어그램이 모바일에서 과도한 빈 공간이나 불필요한 스크롤을 만들지 않는지, 글자 크기를 유지한 채 연결 관계가 읽히는지 확인합니다.
5. 페이지 전체의 가로 스크롤이 생기지 않는지 확인합니다. 표 전용 가로 스크롤이 필요한 경우에는 안내와 조작 가능 여부를 확인합니다.
6. 모바일 화면을 실제로 확인하지 못했다면 확인 완료라고 쓰지 말고 검증하지 못한 범위를 밝힙니다.
